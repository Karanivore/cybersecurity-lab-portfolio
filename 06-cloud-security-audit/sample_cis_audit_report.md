# Cloud Security Audit Report — Sample Engagement

**Scope:** IAM (users, access keys, policies) and S3 (5 buckets)
**Framework:** CIS Amazon Web Services Foundations Benchmark
**Method:** Offline audit of exported IAM/S3 configuration JSON via `scripts/cloud_audit.py`

---

## Executive Summary

The audit identified **19 findings**: 5 Critical, 5 High, 7 Medium, 2
Low. The most urgent issues are an active root account access key with
no MFA, a service account holding full administrative privileges via a
directly-attached wildcard policy, and a publicly-accessible S3 bucket
containing customer invoice data with no encryption. These three should
be remediated immediately; the account should be considered at
meaningful risk of full compromise until they are addressed.

### Deep dive: `customer-invoice-exports`

This bucket is publicly readable (no Block Public Access, permissive
bucket policy), stores customer invoice data, and has no server-side
encryption or access logging enabled. This is the highest-risk finding
in the audit: an unauthenticated party can enumerate and download the
bucket's contents today, and there would be no log trail to detect it.

**Immediate remediation:**
1. Enable all four S3 Block Public Access settings at the bucket level.
2. Remove the public-allowing bucket policy statement; scope access to specific IAM roles.
3. Enable default encryption (SSE-S3 or SSE-KMS) and access logging.
4. Review CloudTrail data-events for this bucket to determine if any unauthorized access already occurred.

### Deep dive: root account + `svc-deploy-bot`

The root account retaining an active access key with no MFA is a
standing critical risk regardless of whether it's actively used — AWS
best practice is zero standing root credentials, MFA-only root login for
emergency use. Separately, `svc-deploy-bot` holds a full-administrator
policy attached directly to the user (not a role), meaning a leaked
credential for this single service account is equivalent to full account
takeover with no assumed-role audit trail.

**Immediate remediation:**
1. Delete the root account's access key; enable hardware/virtual MFA on root; store root credentials per break-glass procedure.
2. Replace `DeployBotFullAccess` with a least-privilege policy scoped to only the actions the deploy pipeline requires.
3. Migrate `svc-deploy-bot` from a static IAM user to an assumed IAM role (e.g. via OIDC federation from the CI/CD provider) to eliminate long-lived credentials entirely.

## Remediation Priority

1. Lock down `customer-invoice-exports` (public data exposure — highest business impact).
2. Remove root access key + enable root MFA.
3. Replace `DeployBotFullAccess` and `AdminRoleForOps` wildcard policies with least-privilege equivalents.
4. Disable the `contractor-temp` access key (unused 311 days) and offboard the account if the engagement has ended.
5. Enable encryption on `corp-shared-docs` and `customer-invoice-exports`.
6. Enable versioning + logging across all buckets currently missing them (defense-in-depth, lower urgency).

## Methodology

Findings were generated by `scripts/cloud_audit.py`, which loads
exported IAM user/policy and S3 bucket configuration JSON and evaluates
each resource against CIS AWS Foundations Benchmark-aligned checks:
root account hygiene (1.4, 1.5), credential lifecycle (1.10, 1.12, 1.14),
least-privilege policy attachment (1.15, 1.16), and S3 public-access,
encryption, versioning, and logging posture (2.1.x, 2.6). In a live
engagement, the same checks run via `boto3` against `iam.list_users`,
`iam.list_policies`, and `s3.get_bucket_*` API calls with read-only
credentials.
